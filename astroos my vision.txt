1. Mission
AstroOS is an enterprise-grade Vedic Astrology Research Platform.

The project is designed for:

Professional Astrologers

Researchers

Students

Institutions

Large-scale Astrology Research

Explainable AI

Statistical Validation

Event Verification

The objective is not merely to generate horoscopes but to build the world's most comprehensive Vedic Astrology Intelligence Platform.

2. Vision
Every prediction produced by AstroOS must be:

Explainable

Traceable

Reproducible

Researchable

Verifiable

No prediction shall exist without supporting calculations and applicable rules.

3. Golden Principles
Architecture before implementation.

Knowledge before prediction.

Research before assumptions.

Deterministic calculations only.

No hidden business logic.

Every decision must be documented.

Every module must remain independently testable.

Every feature must be explainable.

No breaking changes without approval.

Long-term maintainability has priority over short-term speed.

4. AI Governance
No AI agent is allowed to redesign the project independently.

All AI agents must follow:

Constitution

ADRs

Module Contracts

Database Standards

API Standards

If an AI recommends a different design:

Stop implementation.

Produce an ADR proposal.

Wait for approval.

Replit

Code generation

Bug fixing

Architecture

Astrology domain

Change infrastructure decisions

Replace architecture decisions

6. Architecture Rules
Mandatory:

Clean Architecture

Domain Driven Design

SOLID

Repository Pattern

Dependency Injection

CQRS only if justified

Modular Monolith initially

Forbidden:

Circular dependencies

Business logic in controllers

Business logic inside UI

Direct infrastructure access from domain

7. Database Rules
All tables must:

Use UUID primary keys

Support migrations

Be normalized (minimum 3NF)

Include audit timestamps

Define indexes intentionally

Use foreign keys

No table may be renamed after approval without an ADR.

8. API Rules
Every endpoint must have:

Request validation

Response models

Versioning

OpenAPI documentation

Error model

Authentication definition

9. Testing Rules
Every module requires:

Unit tests

Integration tests

Regression tests

Edge case tests

No module is considered complete without passing tests.

10. Documentation Rules
Every module must include:

README

Architecture notes

API documentation

Database impact

Future extension notes

11. Module Completion Criteria
A module is complete only after:

Code complete

Tests passing

Documentation updated

Architecture review approved

Domain review approved

Performance review approved

Security review approved

Every module must stop after implementation.

The following reviews are mandatory:

Architecture

AI compatibility

No subsequent module may begin until approval.

13. Refactoring Policy
Refactoring is permitted only when:

Technical debt is reduced

Maintainability improves

Performance improves

No public contracts break

Otherwise, an ADR is required.

14. Astrology Principles
AstroOS shall never invent astrology.

Every interpretation must be based on:

Classical rules

Approved rule database

Verified calculations

All interpretations must reference their source.

15. Research Principles
Every event entered into the system must be:

Timestamped

Versioned

Reproducible

Linked to calculations

Available for statistical analysis

No research result shall be presented as proof of causation without supporting methodology.

16. Change Management
Every architectural change requires:

ADR

Impact analysis

Approval

Migration strategy

17. Success Criteria
AstroOS is considered successful only if it can:

Generate accurate charts

Explain every prediction

Support large-scale research

Scale to millions of records

Remain maintainable over years of development

One architectural change I recommend
Earlier we planned to start with the Calculation Engine.

I would not do that anymore.

For AstroOS, the order should be:

Phase 0  → Project Foundation
Phase 1  → Domain Model & Astrology Ontology
Phase 2  → Knowledge Base
Phase 3  → Astronomical Calculation Engine
Phase 4  → Chart Engine
Phase 5  → Rule Engine
Phase 6  → Event Engine
Phase 7  → Research Engine
Phase 8  → AI Explanation Engine
Phase 9  → Visualization
This order keeps the project domain-first rather than code-first, which is a much stronger foundation for a research-grade Vedic Astrology platform.
